# rallyr

Turns raw per-shot tennis data into a tidy table of splits, corrections,
and metrics:

- **Splits** unreasonably long rallies back into the real ones a
  sensor/export sometimes merges.
- **Flags and corrects** data-quality issues.
- **Computes** standardised per-session effort and performance metrics.
- **Visualises** it all in a dashboard (planned).

Today the only supported source is the
[SwingVision](https://www.swingvision.com/) app (its public share-link API,
or a raw copy-pasted match/rally page) — that is expected to change, so the
parsing layer is kept separate from the transform/metrics layer it feeds,
deliberately, rather than assuming SwingVision is the only source this
package will ever need. It ships with a synthetic sample dataset, so the
quick-start example below runs with no real session data of any kind.

## Input

The only thing you provide is a **SwingVision share URL** (or bare token)
for one recorded session — everything else is derived from that single
source. `fetch_swingvision()` pulls session-aggregate stats,
`fetch_swingvision_shots()` pulls the per-shot detail, and every other
function (rally splitting, data-quality flags, drill-phase segmentation,
effort metrics) transforms what those two calls returned. There is no other
data entry point.

**Built for structured hitting/rally drills, not scored matches.** The
drill-phase detector (`segment_session_shots()`), and anything conditioned
on its output, was designed for and calibrated against cooperative practice
sessions with distinct drill phases (e.g. a mini-tennis warm-up, net
volleying, cross-court rallies) — not competitive matches with serves,
points, and side-changes. Its default thresholds come from **one** real
drill routine; treat them as a worked example to recalibrate for your own
drills, not a universal setting. If the recorded session is an ordinary
match rather than a drill session, the drill-phase breakdown — and any
metric derived from it — may not mean anything; session- and shot-level
stats (`fetch_swingvision()`, rally splitting, data-quality flags) still
apply regardless of whether the session was a drill or a match.

## Installation

Public on GitHub: <https://github.com/JohnGavin/rallyr>

```r
# install.packages("pak")
pak::pak("JohnGavin/rallyr")
```

## Quick start

The package ships with a bundled synthetic sample database — nothing to
generate first:

```r
library(rallyr)

db_path <- system.file("extdata", "synthetic_sample.duckdb", package = "rallyr")
con <- tennis_db_connect(db_path)

matches <- tennis_matches(con)
matches

schema <- tennis_db_schema(con)   # structure only -- table/column names and types
schema

DBI::dbDisconnect(con, shutdown = TRUE)
```

To parse your own data instead:

```r
# From a SwingVision public share link/token:
match <- fetch_swingvision("https://swing.vision/matches/sw2-...", me = "Your Name")

# From text copied off a SwingVision match/rally page:
matches <- parse_swingvision(pasted_text)
```

## What this package does and does not do

- Parses and stores session-level and shot-level SwingVision data.
- Computes derived metrics: rally splitting (`find_rally_splits()`),
  data-quality flags (`dq_flag_rallies()`, `dq_corrected_rallies()`),
  drill-phase segmentation (`segment_session_shots()`, calibrated for
  practice drills — see **Input** above for why it may not apply to a
  scored match), and standardised per-session effort scores
  (`session_effort_metrics()`).
- Does **not** ship, fetch, or require any real session data — the bundled
  example uses a synthetic dataset generated by `data-raw/generate_sample.R`
  from hand-picked random distributions, never fitted to or derived from
  any real dataset.
- Does **not** yet provide a dashboard or web UI, or a vignette — planned
  (see Roadmap below), not yet built.

## Roadmap

Recorded 2026-09-04, not yet implemented:

- **Source-agnostic transform layer.** SwingVision is the only supported
  source today, but the package's real value is the transform/metrics
  layer downstream of parsing (rally splitting, data-quality correction,
  standardised effort metrics), not the SwingVision-specific parser
  itself. As new sources are added, the transform layer should not need
  to change — only a new source-specific parser producing the same tidy
  shape.
- **Package vignettes.** Currently no `vignettes/` at all.
- **A dashboard vignette populated with simulated data**, built entirely
  on the bundled synthetic sample database — demonstrating the
  transform/metrics/visualisation value this package actually provides,
  not just its data layer. Planning issue:
  [rallyr#1](https://github.com/JohnGavin/rallyr/issues/1).
