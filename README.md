# rallyr

Turns raw per-shot tennis data into a tidy table of splits, corrections,
and metrics:

- **Splits** unreasonably long rallies back into the real ones a
  sensor/export sometimes merges.
- **Flags and corrects** data-quality issues.
- **Computes** standardised per-session effort and performance metrics.
- **Visualises** it in a vignette and in an app that runs in your browser
  (see **Website and browser app**).

Today the only supported source is the
[SwingVision](https://www.swingvision.com/) app (its public share-link API,
or a raw copy-pasted match/rally page). The parsing layer is kept separate
from the transform/metrics layer it feeds, so a future source would only
need a new parser producing the same tidy shape — not a rewrite of the
transform layer itself. It ships with a synthetic sample dataset, so the
quick-start example below runs with no real session data of any kind.

## Input

- One **SwingVision share URL** (or bare token) — e.g.
  `https://swing.vision/matches/sw2-EXAMPLE01` — for one recorded session.
  That's the only thing you provide.
- Everything else is derived from it: `fetch_swingvision()` pulls
  session-aggregate stats, `fetch_swingvision_shots()` pulls per-shot
  detail, and every other function (rally splitting, data-quality flags,
  drill-phase segmentation, effort metrics) transforms what those two calls
  returned.
- No other data entry point.

**Built for structured hitting/rally drills, not scored matches:**

- `segment_session_shots()`'s default thresholds were calibrated against
  **one** real drill routine (mini-tennis warm-up, net volleying,
  cross-court rallies) — treat them as a worked example to recalibrate for
  your own drills, not a universal setting.
- Recorded an ordinary scored match instead? The drill-phase breakdown —
  and anything derived from it — may not mean anything.
- Session- and shot-level stats (`fetch_swingvision()`, rally splitting,
  data-quality flags) still apply either way.

## Quick start

The package ships with a bundled synthetic sample database — nothing to
generate first:

```r
library(rallyr)

db_path <- system.file("extdata", "synthetic_sample.duckdb", package = "rallyr")
con <- tennis_db_connect(db_path)

matches <- tennis_matches(con)
matches

schema <- tennis_db_schema(con)   # structure only -- table/column names and types
schema

DBI::dbDisconnect(con, shutdown = TRUE)
```

To parse your own data instead:

```r
# From a SwingVision public share link/token:
match <- fetch_swingvision("https://swing.vision/matches/sw2-...", me = "Your Name")

# From text copied off a SwingVision match/rally page:
matches <- parse_swingvision(pasted_text)
```

## What this package does and does not do

- Parses and stores session-level and shot-level SwingVision data.
- Computes derived metrics: rally splitting (`find_rally_splits()`),
  data-quality flags (`dq_flag_rallies()`, `dq_corrected_rallies()`),
  drill-phase segmentation (`segment_session_shots()`, calibrated for
  practice drills — see **Input** above for why it may not apply to a
  scored match), and standardised per-session effort scores
  (`session_effort_metrics()`).
- Rally rules (all thresholds in `dq_params()`): stroke limits are per
  drill and count the "me" side's strokes only (cross-court 20, default 25,
  mini-tennis 50); the limit only **flags** a rally and never force-splits
  it. A rally of a cross-court (3 s) or net-volley (2 s) drill is split at a
  pause strictly longer than the threshold when the feeder (`"host"`) hits
  next. A rally holding a single stroke over 160 km/h is flagged, and a drill
  segment shorter than 3 minutes becomes a `"gap"`.
- Parsing notes: the share API is undocumented and unofficial, so any field
  can change or vanish (an absent field parses to `NA`). Spin is
  categorical only (`flat` / `topspin` / `slice`); there is no spin rate
  (rpm) anywhere in the payload. The match-level start time can change
  between fetches of the same match, so it is not an anchor for elapsed
  time; use `video_elapsed_sec` (from the frame number, `fmt_video_time()`
  for display) or the first tracked stroke. Timestamps keep their fractional
  seconds. `sv_video_drift()` checks a recording's frame timing against the
  pinned frame rate.
- Does **not** ship, fetch, or require any real session data — the bundled
  example uses a synthetic dataset generated by `data-raw/generate_sample.R`
  from hand-picked random distributions, never fitted to or derived from
  any real dataset.
- Does **not** run a server: the web app is static and runs in the browser.

## Website and browser app

Documentation site: <https://johngavin.github.io/rallyr/> (reference, news and
a vignette that draws the core charts from the synthetic sample).

The app at <https://johngavin.github.io/rallyr/app/> runs R in your browser
(Shinylive / WebAssembly):

1. Load your **bundle**: one gzip-compressed JSON file of the raw API payloads
   of your past sessions (a synthetic sample is shown until you do).
2. Paste the latest share link. The app shows the API links to open; save each
   as a JSON file (the vendor's server does not let a web page read them
   directly) and drop the files in. The kind of each file is detected from its
   content.
3. Enter your name, add the session (same `match_id`: the newer copy
   replaces the old, and a merge report says what happened) and download the
   updated bundle.
4. The charts are recomputed in the browser with rallyr's own functions. A
   choice above the trend chart puts the oldest session on the left (the
   default) or the newest.

To try the steps without data of your own, two synthetic sets of sample files
ship with the package and are offered for download on the app page ("Try it
with sample files"):

- `inst/extdata/synthetic_sample_bundle.json.gz`: the sample bundle (six
  sessions), for step 1;
- `inst/extdata/synthetic_sample_session/`: one extra session that is not in
  that bundle, as its three raw JSON files (match, stats, shots), for step 2.

```r
extra <- list.files(
  system.file("extdata", "synthetic_sample_session", package = "rallyr"),
  full.names = TRUE
)
bundle <- bundle_read(system.file("extdata", "synthetic_sample_bundle.json.gz", package = "rallyr"))
bundle <- bundle_add_raw(bundle, extra[1], extra[2], extra[3])   # now 7 sessions
```

Privacy: files you choose are read in the browser and are not uploaded. The
app makes no requests to other sites (no analytics, proxy, fonts or scripts
from elsewhere). Two checks run on every build: a scan of the code we ship,
and a real-browser run that fails on any request to another origin. The page
also carries a Content-Security-Policy `<meta>` tag, but that tag does not bind
the Shinylive frame or the workers: the browser check is the real guarantee.

In R, the same bundle can be built and read without the app:

```r
files <- sv_download_raw("https://swing.vision/matches/sw2-...", "raw")
bundle <- bundle_add_raw(bundle_new(), files[["match"]], files[["stats"]], files[["shots"]])
bundle_write(bundle, "my_sessions.json.gz")

derived <- bundle_derived(bundle_to_tables(bundle_read("my_sessions.json.gz"), me = "Your Name"))
plot_session_trend(derived)
```

## API and stability

Derived data is read through five functions that take a database connection
and return tibbles stamped with a `schema_version` attribute:
`rallyr_sessions()`, `rallyr_corrected_rallies()`, `rallyr_session_metrics()`,
`rallyr_net_clearance()` and `rallyr_stroke_quality()`. Their columns and
types are listed once in `rallyr_api_schema()`, and each result is checked
against that list before it is returned. See `?"rallyr-api"`.

Policy, applying from 0.1.0 (the first public release; the package is
pre-1.0 and until then shapes may still change, pinned by a test against
`rallyr_schema_version()`): any change to an output shape (a column added,
removed, renamed, retyped or reordered, or its meaning changed) bumps the
**minor** version and `rallyr_schema_version()`, and is listed in `NEWS.md`;
a patch release then never changes a shape. Recalibrating a `dq_params()` threshold changes
values, not shapes, and is noted in `NEWS.md`; pass `params` to pin the
thresholds an analysis used. Functions outside that list are not covered. There
is no HTTP layer: one would be built only once a real non-R consumer exists.

## Roadmap

Recorded 2026-09-04, not yet implemented:

- **Source-agnostic transform layer.** SwingVision is the only supported
  source today, but the package's real value is the transform/metrics
  layer downstream of parsing (rally splitting, data-quality correction,
  standardised effort metrics), not the SwingVision-specific parser
  itself. As new sources are added, the transform layer should not need
  to change — only a new source-specific parser producing the same tidy
  shape.
- **More vignettes.** One exists (charts from the synthetic sample, rallyr#1);
  guides for the bundle format and for recalibrating drill detection are
  still to do.
